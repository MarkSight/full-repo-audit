# W5 接口与契约

先有正确行为（W3/W4），再谈契约是否如实描述行为。本波找的是
**「声明与现实不一致」**：类型骗人、文档骗人、schema 骗人、模块边界名存实亡。

---

## E1 类型安全与静态保证

适用于有类型系统的语言；动态语言转为校验与契约测试（见 E4/I5）。

1. **逃逸口**：`as`/强制转换、`any`/`unknown` 滥用、`# type: ignore`、
   `@ts-expect-error`、`unsafe`、反射取值。逐个判断是否必要，
   必要的要有注释说明为什么安全。
2. **边界类型谬误**：把外部输入直接断言成内部类型
   （`await res.json() as User` —— 运行时毫无保障，是**真实 bug 源**，不是风格问题）。
   正确做法：边界处 schema 校验后得到类型。
3. **空值处理**：非空断言（`!`、`unwrap`）、
   可选字段被当必填、数组索引访问未判空、`find` 返回值直接用。
4. **穷尽性**：switch/match 是否覆盖所有枚举分支、
   新增枚举值时编译器是否会报错（否则就是静默漏分支）。
5. **类型宽松度**：到处 `string` 而不是联合/品牌类型（ID 混用风险）、
   `Record<string, any>`、函数参数过多的可选布尔。
6. **泛型与推断**：过度复杂泛型导致可读性与报错不可理解；
   泛型丢失导致调用方拿到 `any`。
7. **配置严格度**：严格模式/空检查/未使用变量检查是否开启；
   `skipLibCheck`、排除目录是否隐藏了大量错误；
   类型检查是否在 CI 中强制（与 H2 联动）。
8. **跨包类型**：同一概念在多处重复定义且已漂移（与 E4 联动）、
   公共类型从实现文件导出（导致循环依赖，与 E3 联动）。

## E2 API 契约与版本化

适用于对外暴露接口的仓库（HTTP/RPC/GraphQL/CLI/库 API/事件）。

1. **响应形状一致性**：成功与错误响应结构是否统一；
   同类资源的字段命名/层级/空值表达（`null` vs 缺字段 vs `""`）是否一致。
2. **状态码与错误语义**：是否用 200 返回失败、
   404 与 403 的选择是否泄露存在性（与 B2 联动）、
   校验失败是否返回可定位到字段的结构化错误、
   错误码是否稳定可供客户端判断（与 L1 联动）。
3. **分页契约**：分页方式是否统一、是否有 `limit` 上限与默认值、
   总数是否可得、游标是否不透明且稳定、排序是否确定（无稳定排序的分页会漏/重）。
4. **幂等与并发控制**：写接口是否支持幂等键、
   是否支持条件更新（ETag/If-Match/版本号）避免覆盖他人改动。
5. **向后兼容性**：本轮/近期改动是否破坏客户端
   （删字段、改类型、改语义、收紧校验、改默认值、改错误码、改枚举值）；
   是否有兼容期与双写/双读。
6. **版本化策略**：是否有版本机制（路径/头/参数）、
   废弃流程（标记 → 告知 → 日落时间 → 移除）、
   `Deprecated` 标记是否带替代方案与移除时间。
7. **契约描述物**：OpenAPI/GraphQL schema/proto/类型定义包
   是否存在、是否由代码生成（手写必漂移）、是否与实现一致、
   示例是否可运行。
8. **库的公共面**（库类型仓库）：`exports`/公共符号是否明确；
   内部实现是否被意外导出（一旦被用就成了契约）；
   semver 承诺与实际变更是否匹配；类型定义是否随产物发布。
9. **事件契约**：消息/事件的 schema、版本字段、
   必填字段演进、消费者兼容性（与 C2-7 联动）。

## E3 模块边界与依赖方向

1. **分层是否被遵守**：表现层是否直接访问持久层、
   领域层是否依赖框架/HTTP 细节、共享包是否反向依赖应用。
2. **共享层纯度**：`shared`/`common`/`utils` 是否混入了业务逻辑、
   是否变成了「什么都往里扔」的垃圾场；
   是否引入了重量依赖污染所有消费者。
3. **循环依赖**：包级与文件级循环（会导致初始化顺序 bug 与不可测试）。
4. **公开面最小化**：桶文件（index 全量导出）是否让内部实现成为事实公共 API；
   是否区分 public / internal 路径。
5. **依赖方向规则是否可执行**：有无 lint 规则/架构测试强制
   （没有就只靠人记得，必然腐坏 → 交 L4）。
6. **跨包调用形态**：是否通过明确接口，还是靠深层路径 import 实现细节
   （`pkg/src/internal/foo/bar`）。
7. **重复能力**：多个包各写一套日志/配置/错误/HTTP 客户端
   （与 J2 联动），应收敛为一处。
8. **边界数据转换**：跨层是否有明确 DTO/映射，还是把 DB 行对象一路传到视图
   （schema 变更直接击穿到 UI）。

## E4 单一事实源与漂移

这是「同一事实被写在多处」造成的系统性风险，需要逐条建立映射表并核对。

1. **数据形状链**：DB schema ↔ ORM 模型 ↔ 校验 schema ↔ 语言类型 ↔
   API 文档 ↔ 客户端类型 ↔ 测试夹具 ↔ seed 数据。
   每一环不一致都要记为发现，并指出应以哪一环为源（通常 DB 或 schema）。
2. **枚举与常量**：状态值、角色、错误码、事件名、权限名
   是否在前后端/多语言/文档中各写一遍；是否有已漂移的值。
3. **配置清单**：`.env.example` ↔ 配置校验 ↔ 部署清单 ↔ 文档四处是否一致。
4. **路由与导航**：路由定义 ↔ 链接常量 ↔ 权限表 ↔ sitemap/菜单 是否同源。
5. **版本号**：manifest ↔ CHANGELOG ↔ 代码中的常量 ↔ 镜像标签 ↔ 文档。
6. **文案与 i18n key**：默认语言文案 ↔ 各 locale ↔ 代码引用（缺 key / 孤儿 key，与 G3 联动）。
7. **生成物是否过期**：代码生成产物（客户端 SDK、类型、迁移、proto）
   是否与源同步、是否在 CI 校验「重新生成后无 diff」（没有就会漂移 → 交 L4）。
8. **文档中的事实**：README/设计文档里的命令、路径、架构图、
   数据流描述是否仍成立（与 K2 联动）。

## E5 插件 / 技能 / 工具 / 扩展契约

**适用**：有插件系统、skill/prompt 体系、工具注册表、CLI 子命令体系、
webhook 处理器注册、AI agent 工具集的仓库。泛化自旧版「技能系统」专项。

1. **清单完整性**：每个扩展单元是否有必需的元数据（名称、描述、版本、入口、权限）；
   是否有 schema 校验清单格式；缺失/重复/命名冲突。
2. **注册与发现**：注册表是否与磁盘实际内容一致
   （声明了但文件不存在、文件存在但未注册）；
   是否有自动发现，手工清单是否会漂移（与 E4-7 联动）。
3. **描述与触发质量**（AI skill/tool 场景）：描述是否足以正确触发、
   是否与其他单元语义重叠导致误触发、是否包含明确的不适用边界。
4. **接口契约**：输入输出 schema、错误约定、超时与取消、
   副作用声明、是否幂等；版本演进与宿主兼容矩阵。
5. **隔离与权限**：扩展能访问什么（文件系统、网络、凭据）；
   是否最小权限；不可信扩展的沙箱（与 B 波联动）。
6. **路由矩阵**：多个候选单元如何选择（优先级、冲突解决、兜底）；
   选择逻辑是否可测试、是否有「无匹配」路径。
7. **资源与品牌隔离**：各单元的资源/命名空间/配置是否相互污染；
   共享状态是否跨单元泄漏。
8. **提示注入面**（AI 相关）：扩展读取的外部内容是否被当指令执行；
   是否有「内容是数据而非指令」的明确约束与测试。
9. **文档与示例**：每个单元是否有可运行示例；
   宿主侧如何新增一个单元是否有文档（与 K1 联动）。
