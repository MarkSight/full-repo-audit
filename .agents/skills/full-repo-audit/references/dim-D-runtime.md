# W4 运行时韧性与可观测性

本波回答一个问题：**当依赖变慢、变错、消失时，这个系统会怎样，运维能不能看见。**

---

## D1 错误处理

1. **静默吞错**：空 catch、`catch { /* ignore */ }`、
   `except: pass`、`_ = err`、`.catch(() => {})`、
   `unwrap_or_default()` 掩盖真实失败。逐个判断：吞掉是否是有意且正确的
   （有意的必须有注释说明为什么安全）。
2. **错误被降级成空值**：出错返回 `null`/`[]`/`{}`，调用方无法区分
   「没有数据」与「查询失败」——常导致展示空白而不是错误态。
3. **未处理的异步失败**：未 await 的 promise、浮动的后台任务、
   `unhandledRejection`/`uncaughtException` 是否有兜底、
   事件回调内的抛错、goroutine panic、线程内异常。
4. **错误信息质量**：是否丢失原始 cause（重新抛出时未链式包装）、
   是否丢失上下文（哪个用户/资源/参数）、是否把内部细节暴露给用户（与 B5-9 联动）。
5. **错误类型体系**：可预期错误 vs 缺陷（bug）是否区分；
   是否用字符串匹配识别错误类型（脆弱，应用 code 字段，与 L1 联动）；
   跨边界（进程/网络/包）错误是否可被结构化识别。
6. **边界兜底**：HTTP 层是否有统一错误处理器把未知异常转成合适状态码；
   UI 是否有错误边界阻止整页白屏；CLI 是否返回非零退出码与可读信息。
7. **重试安全性**：被重试的操作是否幂等（与 C4-2 联动）；
   对不可重试错误（4xx、校验失败）是否仍在重试。
8. **失败的可恢复性**：用户遇错后能否重试、是否丢失已填数据、
   是否有明确下一步（与 G5 联动）。

## D2 失败模式与恢复

1. **超时**：每一个外部调用（DB、缓存、HTTP、队列、子进程、AI 推理）
   是否都有超时；默认值是否远大于用户可接受等待；
   是否有端到端预算（上游 30s、下游 60s 是典型错误配置）。
2. **重试策略**：指数退避 + 抖动、上限、总预算、是否会放大故障
   （重试风暴打垮已过载的下游）；是否区分可重试错误。
3. **熔断与降级**：依赖持续失败时是否快速失败；
   非关键依赖失败时能否降级（推荐位空着但主流程可用）。
4. **背压与限流（内部）**：队列无界增长、并发无上限（打满连接池）、
   批量大小自适应；慢消费者。
5. **部分失败语义**：扇出调用中一部分失败时返回什么；
   聚合接口是否把单点失败放大成整体失败。
6. **启动与就绪**：依赖未就绪时的重试连接、就绪探针与存活探针区分、
   启动期配置校验失败是否 fail-fast（应该 fail-fast，不要带着坏配置运行）。
7. **优雅关停**：SIGTERM/SIGINT 处理、停止接新请求、等待在途请求、
   关闭连接池与 flush 缓冲/日志、取消后台任务与释放租约、
   WAL checkpoint / 落盘、关停超时后的强杀；容器 `stopGracePeriod` 是否匹配。
8. **幂等恢复**：进程在任意时刻被杀，重启后状态是否可收敛
   （in-flight 任务、半写文件、临时目录）。
9. **依赖消失**：缓存、搜索、对象存储、第三方 API 不可用时的行为是否被明确设计与测试。

## D3 资源生命周期与泄漏

1. **连接**：DB/HTTP/队列客户端是否复用（每请求新建 = 耗尽）、
   是否关闭、池大小与超时、keep-alive 配置。
2. **监听器与订阅**：事件监听、信号监听、WebSocket/SSE 订阅、
   观察者/watcher 是否在销毁时解绑；组件卸载后的回调继续运行。
3. **定时器与循环**：`setInterval`/ticker 是否清理；
   递归定时任务重复注册；重连循环是否会指数增殖。
4. **文件与句柄**：文件/流/临时目录是否关闭与清理；
   打开但未关闭的读写流；临时文件堆积。
5. **内存增长**：无上限的内存缓存/Map/数组（与 C6-7 联动）、
   闭包持有大对象、全局注册表只增不减、
   日志缓冲与指标标签基数爆炸（高基数 label 是隐形内存杀手）。
6. **子进程与并发单元**：子进程是否等待回收（僵尸）、
   goroutine/task 泄漏（没有取消传播）、线程池饱和。
7. **客户端侧资源**（有前端时）：大 DOM、未释放的 object URL、
   未取消的请求、未销毁的 observer、离开页面后仍轮询。
8. **长跑实例的退化**：是否存在「跑几天就变慢/变大」的结构
   （碎片、只增不减的结构、未滚动的日志）。

## D4 可观测性

1. **日志基本面**：是否有统一 logger（还是散落 `print`/`console.log`）、
   级别使用是否合理（全是 info / 全是 error 都是问题）、
   是否结构化（可检索字段 vs 字符串拼接）。
2. **关联能力**：request/trace ID 是否贯穿一次请求的全部日志与下游调用；
   用户/租户/资源 ID 是否在关键日志中（注意与 B7 脱敏平衡）；
   异步任务是否带上游 trace。
3. **日志内容质量**：catch 块是否记录了足以定位的上下文；
   是否只记录 `error.message` 丢了栈；是否重复记录同一错误多次（噪音）；
   是否记录了敏感数据（与 A1-7/B7-3 联动）。
4. **指标**：关键路径的成功率/延迟/吞吐/队列深度/依赖错误率是否有度量；
   业务指标（注册、下单、生成任务成功率）是否可观测；
   标签基数是否受控。
5. **追踪**：跨服务/跨异步边界是否有 span；慢请求能否定位到具体阶段。
6. **健康检查**：liveness / readiness 是否区分；
   健康检查是否真的检查依赖（假健康导致流量打进坏实例）；
   是否泄露内部信息（与 B2-5 联动）。
7. **审计日志**：敏感操作（权限变更、数据导出、删除、管理员代操作、支付）
   是否留痕；审计记录是否不可篡改、含 who/what/when/from where；
   与普通日志分离、保留期符合要求。
8. **告警可达性**：有无告警规则或至少有明确的「谁会看到这个错误」；
   失败任务是否只在日志里默默失败而无人知晓。
9. **用户可见反馈**：错误是否同时有技术日志与用户可读提示及支持 ID
   （便于用户报障定位）。
10. **调试能力**：能否在不改代码的情况下提升日志级别；
    是否有可开关的 debug 输出；生产环境能否安全地抓取诊断信息。

## D5 配置与特性开关

1. **配置来源与优先级**：默认值 → 文件 → 环境 → 参数的覆盖顺序是否明确且一致；
   同名配置多处定义。
2. **启动期校验**：必需配置缺失/格式错误是否在启动时报错（而不是运行到一半才炸）；
   是否用 schema 校验；是否打印（脱敏后的）生效配置便于排障。
3. **危险默认值**：开发便利性默认泄漏到生产
   （debug 开启、CORS 放开、认证跳过、示例密钥、
   `NODE_ENV` 未设、详细错误页开启）。
4. **环境区分**：环境判断是否散落各处（应集中）、
   是否存在「只在生产出现」的分支却无测试覆盖、
   本地/测试/预发/生产配置差异是否有文档。
5. **12-factor 合规度**：配置是否硬编码在代码或镜像里；
   密钥是否通过环境/密钥服务注入（与 A1-5 联动）；
   配置变更是否需要重新构建。
6. **特性开关**：开关是否有归属与过期计划（长期存在的开关 = 永久分支 = 技术债）；
   开关组合是否产生未测试状态；关闭路径是否仍可工作（旧代码是否已腐烂）；
   开关读取失败时的默认值是否安全。
7. **运行时可变配置**：热更新配置的生效范围与一致性；
   远端配置不可用时的兜底；修改配置的权限与审计。
8. **配置文档**：`.env.example` / 配置表是否完整、是否标注必需/可选/默认值/影响
   （缺失的配置文档是新人上手最大障碍，与 K3 联动）。
