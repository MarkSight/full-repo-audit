# W8 交付与运维

审查对象是「从源码到生产」这条链路本身。它的缺陷不会在代码评审里暴露，
但会在发布日造成最大损失。

---

## H1 构建与可复现性

1. **一条命令可构建**：从干净克隆到可运行产物的步骤是否文档化且可跑通；
   是否依赖某人机器上的隐性状态。
2. **确定性**：同一 commit 构建两次产物是否一致；
   是否依赖构建时网络、当前时间、随机数、本地时区、
   未钉死的工具链版本（Node/Python/Go/Rust 版本是否有 `.tool-versions`/`.nvmrc` 等声明）。
3. **环境隔离**：构建是否读取了本地 `.env` 导致把开发配置打进产物；
   产物中是否含开发用调试代码/源映射（源映射泄露源码，与 B5-9 联动）。
4. **产物正确性**：入口与导出是否正确、
   是否包含不该发布的文件（测试、夹具、密钥、内部文档）、
   `files`/`MANIFEST`/`.dockerignore` 白名单是否准确。
5. **生成产物提交策略**：构建产物是否被提交进仓库
   （若是，是否有再生成校验，与 E4-7 联动）。
6. **多目标构建**：多平台/多架构/多运行时目标是否都被验证。
7. **构建告警**：是否有被长期忽略的构建警告（警告即未来的错误）。

## H2 CI/CD 正确性与安全

1. **门禁完整性**：format/lint/typecheck/test/build 是否都在 CI 跑；
   是否为**必需检查**（配置成可跳过就等于没有）；
   是否只在部分分支/路径触发而漏掉关键改动。
2. **与本地一致**：CI 与本地用同一命令与同一工具版本
   （不一致会出现「本地过 CI 不过」的长期摩擦）。
3. **安装可复现**：使用 frozen/ci 安装模式；缓存键是否包含锁文件哈希；
   缓存是否可能投毒（与 A3 联动）。
4. **权限最小化**：workflow token 权限是否默认只读、
   按 job 提升；是否使用 OIDC 而非长期云凭据；
   secrets 是否只注入到需要的 job。
5. **不可信输入**：fork PR 的工作流是否能拿到 secrets
   （`pull_request_target` + 检出 PR 代码 = 高危）；
   是否在日志中打印 secrets；
   是否把 PR 标题/分支名等不可信字符串直接拼进 shell（命令注入）。
6. **Action/第三方步骤固定**：是否钉到 commit SHA 或至少固定版本；
   自托管 runner 的隔离。
7. **流水线可靠性**：是否有长期 flaky 被 `continue-on-error` 掩盖、
   是否有被注释掉的检查、重试是否掩盖真实失败、超时设置。
8. **发布流水线**：发布是否自动化且可追溯（谁发的、发了哪个 commit）；
   是否需要人工审批；
   发布失败的回滚路径；
   制品签名/attestation（与 A3-7 联动）。
9. **并发与顺序**：同分支并发部署的竞态、
   是否有部署锁、
   迁移与部署的顺序保障（与 C2-2 联动）。
10. **分支保护与评审**：直接推主干是否可能、
    CODEOWNERS 是否覆盖关键目录、
    合并策略是否一致。

## H3 容器与基础设施即代码

**适用**：存在 Dockerfile / compose / k8s / helm / terraform / ansible / pulumi。

1. **镜像基线**：基础镜像是否钉版本（非 `latest`）、是否精简、
   是否定期更新；是否存在已知漏洞（trivy 等扫描）。
2. **权限**：是否以 root 运行、
   是否需要特权/额外 capability、
   只读根文件系统可行性、
   挂载的宿主路径与 socket（`docker.sock` 挂载 = 等同宿主 root）。
3. **构建质量**：多阶段构建、层顺序与缓存、
   `.dockerignore` 是否排除 `.git`/`node_modules`/密钥、
   构建参数是否把 secrets 留在镜像层（`--build-arg` 会留痕，应用 secret mount）。
4. **运行时配置**：健康检查定义、
   资源 requests/limits、
   停止信号与优雅期（与 D2-7 联动）、
   日志输出到 stdout、
   时区与 locale。
5. **k8s/helm**：探针正确性（liveness 用了重依赖检查会造成级联重启）、
   副本数与 PDB、
   secrets 管理方式（明文 ConfigMap 是问题）、
   网络策略、
   资源配额、
   滚动更新参数与零停机前提。
6. **IaC 安全**：公开的存储桶/安全组 0.0.0.0/0、
   未加密的卷与备份、
   过宽的 IAM 角色、
   状态文件存放与锁（terraform state 含敏感值）。
7. **漂移与一致性**：IaC 是否真实反映线上（手工改过的资源）、
   多环境配置的差异是否可见、
   是否有 plan 审查流程。
8. **本地环境对齐**：compose 配置是否与生产拓扑近似
   （差异过大会让本地测不出问题）。

## H4 部署、回滚与运行期变更

1. **部署方式**：滚动/蓝绿/金丝雀；
   是否要求新旧版本共存期兼容（与 C2-2、E2-5 联动）。
2. **回滚能力**：能否一键回滚到上一个版本；
   回滚时数据库迁移怎么办（不可逆迁移会让回滚失效——必须显式评估）。
3. **零停机前提**：连接排空、
   长连接/SSE/WebSocket 的断开处理、
   在途任务的继承、
   缓存预热。
4. **配置变更流程**：环境变量/密钥变更是否需要重启、
   变更是否有记录与审批、
   错误配置的影响半径与快速恢复。
5. **迁移执行**：谁来跑、跑失败怎么办、
   是否有超时与锁监控、
   是否在部署流程中阻塞式执行大迁移。
6. **发布后验证**：是否有冒烟检查/健康验证/关键指标观察窗口；
   谁负责盯、盯多久。
7. **事故准备**：runbook 是否存在（常见故障的处理步骤）、
   on-call 与升级路径、
   功能开关可否快速关闭新功能（与 D5-6 联动）。
8. **环境清单**：有哪些环境、各自用途与数据敏感度、
   谁可访问、
   预发是否使用生产数据（合规风险，与 B7 联动）。

## H5 发布与版本纪律

1. **版本号**：是否遵循 semver（或明确的其他方案）、
   破坏性变更是否升主版本（与 E2-5 联动）、
   多包仓的版本联动策略。
2. **CHANGELOG**：是否维护、
   是否面向使用者（而不是 commit 日志复制）、
   是否标注破坏性变更与迁移指引、
   未发布段落是否存在。
3. **提交与 PR 纪律**：提交信息是否可追溯意图、
   是否有 squash 导致历史不可读或相反的噪音历史、
   PR 是否关联 issue/设计文档。
4. **标签与产物对应**：git tag ↔ 版本号 ↔ 发布产物 ↔ 镜像标签 是否一一对应可追溯。
5. **废弃流程**：废弃标记、日落时间、
   通知渠道、
   移除是否按期执行（长期「待移除」是债）。
6. **文档随发布更新**：README/迁移指南/API 文档是否与版本同步（与 K2 联动）。
