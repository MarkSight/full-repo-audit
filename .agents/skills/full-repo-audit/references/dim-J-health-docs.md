# W10 代码健康与文档

本波的发现多为 Medium/Low，但它们决定**下一次改动有多贵**。
要求：每条发现都要能说明「留着它的具体代价」，否则不入台账
（避免把审查变成风格偏好清单）。

---

## J1 死代码与未使用资产

1. **未使用导出**：跨全仓搜索引用；注意动态引用（字符串路由、反射、
   配置中引用的名字）会造成误判——删除前必须确认。
2. **仅被测试引用的生产代码**：要么是该删的遗留，要么是测试在测无人使用的东西。
3. **不可达分支**：永假条件、已过期的版本判断、
   已完成的迁移兼容分支（「兼容旧数据」的代码在数据已全部迁移后应删）。
4. **注释掉的代码**：一律删除（版本控制就是历史），
   除非注释里说明了为什么保留与何时恢复。
5. **未使用的依赖**：清单中声明但无引用的包；
   反向：被引用但未声明（靠传递依赖可用，随时会断）。
6. **未使用的资源与配置**：图片/字体/图标/翻译 key/环境变量/
   特性开关/数据库列与表/索引；一次性脚本与废弃工具。
7. **僵尸文件**：旧版本备份（`foo.old.ts`、`foo copy.ts`）、
   个人临时文件、`.orig`/`.rej` 冲突残留。
8. **删除前的确认流程**：动态引用检查 + 全仓搜索 + 运行测试；
   不确定的归入「建议删除（待确认）」而不是直接删。

## J2 重复与缺失抽象

1. **同一逻辑多处实现**：校验规则、权限判断、格式化、
   错误构造、HTTP 客户端封装、日期处理、分页逻辑。
   重复的**校验与权限**逻辑是 High（会出现某处被修某处没修）。
2. **近似复制粘贴**：整块相似代码仅少量差异；
   判断是否应抽象（有真实共同语义）还是应保持分离（偶然相似）。
3. **数据访问重复**：相似查询散落各处而非收敛到仓储层。
4. **测试重复**（与 I4-3 联动）、夹具重复、配置重复（多处定义同一常量）。
5. **文档重复**：同一事实写在多篇文档中（必然漂移，应单处 + 链接）。
6. **过度抽象的反向问题**：只有一个实现的接口、
   为假设的未来需求做的参数化、
   三层包装只为调一个函数——这类也要报（抽象债与重复债同样昂贵）。
7. **取舍原则**：三处以上重复且语义相同 → 建议抽象；
   两处 → 通常保留；
   抽象会引入跨层依赖 → 宁可重复。

## J3 耦合、内聚与拆分

1. **超大文件/函数/类**：按语言惯例给出阈值依据
   （不是单纯行数，而是职责数与修改原因数）；
   指出应如何按职责切分，而不是机械按行数切。
2. **职责混合**：同一文件里同时做 HTTP 解析 + 业务规则 + 持久化 + 格式化。
3. **上帝对象与全局状态**：被所有模块依赖的超级对象、
   可被任意处修改的全局状态、
   模块级可变单例（与 C4-6 联动）。
4. **隐式耦合**：靠执行顺序、靠副作用、靠共享临时目录/全局变量通信；
   改 A 必须同时改 B 但没有任何静态关联。
5. **硬编码依赖**：无法在测试中替换的直接构造（与 I3-6 联动）；
   写死的路径/URL/租户/语言/时区。
6. **扇入扇出异常**：被 50 处引用的工具文件（改动风险集中）、
   依赖 30 个模块的单个文件（理解成本）。
7. **拆分建议要可执行**：给出目标结构、迁移顺序、
   如何保持每一步都可运行与可回滚；
   不可执行的「建议重构」不入台账（改为 deferred 并写明前置条件）。

## J4 命名与风格一致性

统一原则：**以仓库现状中的多数派为准**，除非多数派本身有害。
每条发现要指出「现有约定是什么、此处如何偏离」。

1. **路径与文件名**：目录命名风格（kebab/snake/camel）、
   文件名与主导出是否一致、
   扩展名选择是否一致、
   测试文件位置与命名。
2. **标识符命名**：函数动词短语、布尔前缀（`is/has/should`）、
   事件处理前缀、
   类型/接口/枚举命名、
   常量、
   缩写使用是否一致、
   单复数（集合用复数）。
3. **领域术语**：同一概念的代码命名是否统一（与 G7-1 联动，应与 UI 术语一致）。
4. **导入与导出**：顺序与分组、类型导入写法、
   命名导出 vs 默认导出、
   桶文件策略、
   相对路径 vs 别名路径。
5. **代码风格模式**：错误处理风格（返回 Result vs 抛异常）是否统一、
   空值合并与默认值写法、
   异步风格（promise chain vs async/await）、
   条件表达方式、
   早返回 vs 嵌套。
6. **格式化**：是否有格式化工具且被强制（若有，风格问题应由工具解决，
   不要人工逐条报——直接报「未启用/未在 CI 强制」一条即可，交 L4）。
7. **配置一致性**：多包仓中各包的 tsconfig/lint 配置/脚本名是否一致；
   脚本名语义统一（`test`/`check`/`build` 在各包含义相同）。

## J5 注释与 TODO 债

1. **错误的注释**：与代码不符的注释（比没有注释更坏，按 Medium 起步）。
2. **无价值注释**：复述代码的注释、
   自动生成的空模板文档、
   分隔线装饰。
3. **缺失的「为什么」**：非显然的约束、
   绕过某 bug 的 workaround、
   性能权衡、
   不可变顺序要求——这些**必须**有注释，缺失即发现。
4. **抑制注释**：lint/type 抑制是否有理由说明与范围最小化（与 E1-1 联动）。
5. **TODO/FIXME/HACK 台账**：逐条归类为
   （a）真实缺陷 → 转为正式发现
   （b）已过期 → 删
   （c）有效待办 → 登记到 deferred 并带 owner
   （d）无信息量 → 删。
   **不要把 TODO 数量当作发现，要把每条 TODO 处理掉。**
6. **公共 API 文档注释**：对外暴露的函数/类型是否有用法说明、
   参数约束、抛错说明（库类型仓库按 High 要求）。

## J6 仓库卫生

1. **不该入库的内容**：构建产物、缓存目录、依赖目录、
   日志、临时文件、IDE 个人配置、
   本地数据库文件、大型二进制、
   操作系统垃圾文件（`.DS_Store`）。
2. **仓库体积**：大文件清单与历史膨胀（历史中的大文件即使删了仍在 `.git` 中）；
   是否需要 LFS。
3. **忽略规则**：`.gitignore` 是否覆盖实际产物目录；
   是否过宽以致误忽略源文件；
   `.gitattributes`（行尾、二进制标记、linguist）。
4. **静态资源**：未使用资源、未压缩图片、
   重复资源、
   字体子集与格式、
   缺失的标准文件（favicon、`robots.txt`、`manifest`、`sitemap`——按项目类型判断）。
5. **输出目录**：`outputs/`、`tmp/`、`reports/` 这类运行时目录
   是否被忽略且有清理策略。
6. **分支与标签卫生**：已合并分支堆积、
   长期未合并的分支（冲突成本）、
   标签命名混乱。

# K 文档与开发者体验

## K1 文档完备性

按「新人第 1 天 / 第 1 周 / 值班夜里」三个场景检查文档是否够用。

1. **README**：项目是做什么的、
   如何跑起来（可验证的步骤）、
   如何跑测试、
   目录结构导览、
   如何贡献、
   许可证。
2. **架构文档**：系统组成与边界、
   关键数据流、
   依赖的外部服务、
   重要约束与非目标；
   图是否与现状一致（与 K2 联动）。
3. **决策记录（ADR）**：重要技术取舍是否有记录（为什么选 A 不选 B）；
   没有记录的决策会被后人无意推翻。
4. **运行手册（runbook）**：常见故障处置、
   如何查日志与指标、
   如何回滚、
   如何执行迁移、
   联系人与升级路径（有生产系统则按 High 要求）。
5. **API/接口文档**：是否存在、是否与实现同源（与 E2-7 联动）。
6. **配置文档**：所有环境变量/配置项的作用、必需性、默认值、影响面（与 D5-8 联动）。
7. **安全文档**：`SECURITY.md`（漏洞报告渠道）、
   威胁模型（有敏感数据则要求）、
   权限模型说明。
8. **贡献与规范**：`CONTRIBUTING.md`、
   提交规范、
   评审要求、
   发布流程。
9. **领域知识**：业务术语表、
   状态机图、
   权限矩阵——
   这些无法从代码读出的知识是否被写下来。

## K2 文档准确性与交叉引用

1. **可执行性验证**：文档里的命令逐条实际跑一遍（至少语法与路径核对）；
   跑不通的命令是 High（新人第一天就会撞上）。
2. **陈述与现实核对**：目录结构、文件路径、架构图、
   技术栈版本、端口、环境变量名、示例代码。
3. **链接健康**：内部相对链接、锚点、外部链接（至少检查明显失效域名）、
   图片引用。
4. **版本一致性**：文档中的版本号 ↔ manifest ↔ CHANGELOG（与 E4-5 联动）。
5. **重复与矛盾**：两处文档对同一事实说法不同——必须指出哪个是对的。
6. **过期文档**：描述已删除功能的文档、
   历史方案文档是否标注「已归档/历史参考」。
7. **文档位置可发现性**：文档是否散落在多处无索引；
   README 是否链接到关键文档。

## K3 开发者体验与本地环境

1. **冷启动成本**：从克隆到跑起来需要多少步、多少隐性知识、
   是否有一条命令（setup 脚本/容器化）；实测可行性。
2. **本地依赖**：需要的外部服务（DB/缓存/队列）是否有 compose 或替身；
   是否必须连接真实云服务才能开发。
3. **反馈循环**：热重载、
   watch 模式、
   只跑受影响测试、
   类型检查速度（与 F4/I4 联动）。
4. **质量自助**：一条命令跑全门禁（`make check` 之类）、
   自动修复命令、
   pre-commit hook 是否存在且不过慢（过慢会被 `--no-verify` 绕过）。
5. **调试支持**：调试配置、
   日志级别开关、
   种子数据与测试账号、
   如何复现线上问题。
6. **脚本质量**：脚本是否有 `set -euo pipefail`、
   是否有帮助说明、
   是否幂等、
   跨平台（macOS/Linux/Windows）可用性。
7. **编辑器与工具约定**：`.editorconfig`、
   推荐插件、
   格式化与 lint 的编辑器集成，
   避免「每个人保存后 diff 不同」。
8. **新人可验证性**：是否有「按文档走一遍就能完成一个小改动并通过门禁」的路径
   （onboarding 的实际检验标准）。
