# W11 跨切面治理与门禁固化

前十波找的是**具体缺陷**，本波找的是**让缺陷可以重复发生的结构**，
并把本轮结论固化成自动检查。

**本波的产出必须包含至少一条新增的自动化门禁**，否则下一轮审查会重复发现同样的问题。

---

## L1 错误码与错误分类学

1. **清点**：列出所有错误类型/错误码/错误常量，
   检查命名格式是否统一、是否有重复语义的不同码、是否有未使用的码。
2. **结构化识别**：错误是否带稳定的机器可读标识
   （而不是靠 message 字符串匹配——这会在改文案时静默破坏调用方）。
3. **分类维度**：是否能区分
   客户端错误 / 权限错误 / 未找到 / 冲突 / 限流 / 依赖故障 / 内部缺陷；
   每类是否映射到一致的 HTTP 状态码/退出码/日志级别/是否可重试。
4. **跨边界传播**：错误穿过网络/进程/包边界后是否仍可被分类识别；
   是否保留 cause 链（与 D1-4 联动）。
5. **用户可见映射**：每个错误码是否有对应的用户文案与下一步建议
   （与 G5-4/G7-4 联动）；是否有兜底文案。
6. **文档与契约**：错误码是否对外文档化、是否纳入 API 契约（与 E2-2 联动）。
7. **固化**：新增错误类型是否有格式检查（lint 规则或测试）。

## L2 日志格式与遥测统一

1. **入口统一**：是否所有日志经由同一 logger
   （散落的 `print`/`console.log` 数量与位置清单）。
2. **字段约定**：统一字段名（`level`/`msg`/`trace_id`/`user_id`/`err`）、
   统一前缀或模块标识、
   统一时间格式与时区。
3. **级别约定**：各级别的使用标准是否被写下来并遵守
   （何时 warn 何时 error；error 是否意味着需要人处理）。
4. **噪音治理**：高频重复日志、
   正常流程打 error、
   同一错误在多层各记一遍；
   是否有采样/去重。
5. **脱敏约定**：敏感字段清单与统一脱敏函数（与 B7-3 联动），
   而不是靠每个调用点自觉。
6. **指标与事件命名**：度量/埋点命名规范、标签基数约束（与 D4-4 联动）。
7. **固化**：是否有 lint 规则禁止裸 `console.log`/`print`、
   是否有测试校验日志结构。

## L3 跨切面模式一致性

逐项确认「同一件事在全仓是否只有一种做法」，不一致处列出全部位置并给出收敛目标：

1. 时间的获取与格式化（是否有统一 `now()`/时钟抽象，便于测试与一致性）。
2. ID 生成（策略、长度、可排序性）。
3. 分页（参数名、默认值、上限、返回结构）。
4. 排序与过滤参数表达。
5. 成功/失败返回风格（Result vs 异常，与 J4-5 联动）。
6. 输入校验入口（是否都经过同一校验层，与 B3-1 联动）。
7. 权限判定入口（是否都经过同一策略层，与 B2-2 联动）。
8. 配置读取（是否都经过同一配置模块，与 D5-1 联动）。
9. 数据访问（是否都经过仓储/DAO 层，与 J2-3 联动）。
10. 外部调用（是否统一封装了超时/重试/日志/指标，与 D2 联动）。
11. 缓存访问（键构造与失效是否统一，与 C6-2 联动）。
12. 事务边界的开启方式（与 C1-2 联动）。
13. 文案与 i18n 取用（与 G3-1 联动）。
14. 特性开关读取（与 D5-6 联动）。

对每项给出：现状做法数量 → 推荐收敛目标 → 迁移成本估计 → 是否可加门禁。

## L4 门禁固化与归属

把本轮的发现转化成**不依赖人记性的机制**。按下列优先级产出清单：

1. **可 lint 的**：命名、导入方向、禁用 API、裸日志、
   危险函数（`eval`、`dangerouslySetInnerHTML`、非参数化 SQL）、
   抑制注释需带理由、依赖方向（架构 lint）。
   → 写成规则并在 CI 强制（与 H2-1 联动）。
2. **可测试的**：授权矩阵、错误码格式、
   契约快照（API/事件/公共导出）、
   配置清单完整性、
   生成物无 diff、
   i18n key 完备性、
   迁移可回滚。
   → 写成测试（优于文档）。
3. **可脚本化的**：机密扫描、依赖审计、许可证检查、
   体积预算、
   死代码扫描、
   链接检查。
   → 加到 CI 或 pre-commit（注意耗时，与 K3-4 联动）。
4. **只能靠流程的**：设计评审、
   破坏性变更的兼容期、
   CODEOWNERS 覆盖关键目录、
   发布审批、
   事故复盘。
   → 写进 CONTRIBUTING / PR 模板 / 文档，并指出归属。
5. **门禁本身的质量**：新增门禁是否会产生误报（误报率高的门禁会被绕过）、
   是否可快速运行、失败信息是否能指导修复、
   是否有豁免机制与豁免记录。
6. **归属明确**：每个新增门禁/每条延期项指定 owner 与期限；
   无人负责的待办等于不存在。
7. **反向检查**：现有门禁中是否有**形同虚设**的
   （被 `continue-on-error`、被排除目录、阈值过低、长期失败被忽略）——
   这些比没有门禁更危险，因为它提供虚假安全感。
