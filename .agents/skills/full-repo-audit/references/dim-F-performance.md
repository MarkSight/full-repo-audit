# W6 性能与资源效率

放在正确性之后：不给将要被改写的代码做优化。
**本波只报「有证据的」性能问题**——能指出复杂度、调用次数、载荷大小或实测数据。
「看起来可以更快」不入台账。

---

## F1 算法与热点复杂度

1. 嵌套循环上的数据规模是否有界；`O(n²)` 出现在用户可控规模上（列表、批量导入、
   权限计算、diff、去重）。
2. 在循环里做昂贵操作：正则编译、JSON 序列化、深拷贝、
   排序、数据库查询、加密、日志格式化。
3. 数据结构选择：数组做成员判断（应用 Set/Map）、
   重复线性查找、频繁首部插入、大对象反复展开复制。
4. 不必要的重复计算：同一请求内多次重算同一结果（缺少请求级 memo）；
   派生数据每次渲染/调用都重算。
5. 字符串与缓冲：大字符串累加拼接、反复 `split/join`、
   大 JSON 全量解析（可流式处理的场景）。
6. 递归深度与栈溢出风险；尾递归假设不成立的语言。
7. 正则性能：回溯爆炸（与 B6-4 联动）、在热路径上未预编译。
8. 大数据集处理：是否全量载入内存（应流式/分页/分块）；
   导出与报表的内存峰值。

## F2 I/O 与网络效率

1. **串行等待**：可并行的独立请求被顺序 await（最常见且收益最大的问题）；
   循环内逐条查询（N+1，与 C3-4 联动）。
2. **批量化**：是否支持批量接口/批量写/批量加载（dataloader 模式）；
   批量大小是否合理（太大引发超时与锁）。
3. **载荷大小**：返回未使用的字段与关联、缺少字段投影、
   未压缩响应、过度嵌套、base64 嵌入大二进制。
4. **连接复用**：HTTP keep-alive / 连接池 / DNS 缓存；
   每次调用新建客户端（与 D3-1 联动）。
5. **缓存机会**：稳定的昂贵计算/远程调用是否有缓存（与 C6 协同，注意正确性优先）。
6. **文件与对象存储**：是否经由应用中转大文件（应用预签名 URL 直传/直下）；
   是否一次读整个文件；临时文件写放大。
7. **数据库往返**：同一逻辑多次往返（可合并为一条语句/一个事务）；
   事务内等待外部 IO（与 C1-3 联动）。
8. **后台与前台分离**：用户请求里做本应异步的重活
   （发邮件、生成报表、调用 AI、图像处理）导致长响应。

## F3 客户端性能与预算

**适用**：有前端/移动端的仓库。

1. **包体积**：总体积与首屏 JS 预算、是否有体积监控、
   重复依赖、未 tree-shake 的整包引入（`import _ from 'lodash'`）、
   大依赖（moment/icon 全集/图表库）是否可替换或按需加载。
2. **代码分割**：路由级/组件级懒加载、
   关键路径与非关键路径区分、预取策略。
3. **渲染性能**：不必要的重渲染（缺少 memo/key 错误/每次新建引用）、
   长列表未虚拟化、大 DOM 节点数、同步布局抖动、
   主线程长任务、昂贵计算未移出渲染路径。
4. **资源加载**：图片尺寸与格式（响应式/现代格式/懒加载）、
   字体加载策略与子集化、阻塞渲染的 CSS/JS、
   第三方脚本的成本与失败影响。
5. **网络层**：请求瀑布、重复请求、缺少去重与取消、
   轮询频率、过度的实时连接、离线/弱网表现。
6. **Web 指标**：LCP/CLS/INP 的明显结构性问题
   （无尺寸占位的图片、字体切换跳动、首屏依赖客户端数据）。
7. **缓存与版本**：静态资源指纹与长缓存、HTML 不被长缓存、
   Service Worker 的更新与陈旧内容问题。
8. **预算是否被守卫**：有无体积/性能预算检查在 CI（没有 → 交 L4）。

## F4 构建与启动性能

1. 构建耗时与增量能力、缓存命中（本地与 CI）、
   是否每次全量重建、任务编排是否并行。
2. 类型检查/lint/测试耗时是否已影响开发循环（与 I4/K3 联动）。
3. 产物大小与分层（容器镜像层顺序、多阶段构建、`.dockerignore`，与 H3 联动）。
4. 冷启动：无服务器/容器启动耗时、启动时的同步初始化、
   预热需求、依赖加载（按需 require vs 顶层全量）。
5. 开发体验：热更新是否可用且快、watch 模式是否频繁全量重算。
6. 产物是否被重复构建（多个流程各建一次）。

## F5 基准与回归守卫

1. 有无关键路径的基准测试或负载测试；是否记录过基线数据。
2. 性能回归是否可被发现（CI 基准、体积对比、慢查询日志、APM 告警）。
3. 容量假设是否写下来（预期 QPS、数据量、并发、单条大小上限）；
   代码中的隐含假设（「数据不会超过 1000 条」）是否有约束或告警。
4. 压测覆盖的失败模式：过载下的行为、限流是否生效、
   降级是否符合预期（与 D2 联动）。
5. 成本视角：昂贵外部调用（AI 推理、地图、短信）的用量监控与上限
   （与 B6-7 联动）。
6. 本波的建议是否需要先加度量再优化——**没有度量就不要改热路径**，
   写成「先加基准」的发现，而不是直接改代码。
