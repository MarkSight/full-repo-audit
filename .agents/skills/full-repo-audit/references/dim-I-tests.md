# W9 测试体系

放在修复之前：W13 的修复需要可信的门禁。测试体系本身不可信时，
先修测试能力，再修业务代码。

**核心判据不是覆盖率数字，而是「如果这里坏了，哪个测试会红」。**
对每条 Critical/High 发现，都要能回答这个问题；答不出来就是覆盖缺口。

---

## I1 风险导向的覆盖缺口

1. **关键路径映射**：把认证、授权、支付/计费、数据写入、迁移、
   权限判定、外部集成、状态机转移逐条列出，标注「有/无」测试。
   无测试的关键路径一律 High。
2. **本轮发现的回归保护**：W1-W8 每条已确认缺陷，是否存在会失败的测试？
   修复时必须**先写失败测试再修**（否则无法证明修好了）。
3. **分支与边界覆盖**：错误分支、空集合、单元素、
   最大值、并发路径、超时路径、权限拒绝路径——
   通常只有 happy path 被测。
4. **覆盖率的正确用法**：看**未覆盖的关键文件清单**，不看总百分比；
   有覆盖率工具但无阈值、或阈值远低于实际值（形同无门禁）都要记录。
5. **测试金字塔形状**：是否倒置（大量慢 e2e，缺少快速单测）或
   只有单测而无任何集成验证（单测全绿但组合起来不工作）。
6. **契约覆盖**：对外 API/事件/库公共面是否有契约测试
   （防止 E2-5 的破坏性变更，没有就交 L4）。
7. **迁移与数据层**：迁移是否被测试（正向、回填、旧数据兼容）；
   复杂查询是否有针对真实数据库的测试（而不是全 mock）。

## I2 断言强度与测试有效性

1. **弱断言**：`toBeDefined`、`toBeTruthy`、`not.toThrow`、
   只断言调用次数不断言内容、只断言状态码不断言响应体、
   断言 `length > 0`。逐个强化为对具体值/结构的断言。
2. **无断言测试**：只执行代码不校验结果（只能发现崩溃）；
   断言写在回调里但回调未必执行（异步测试陷阱）。
3. **测试是否真的会失败**：对可疑测试做**变异验证**——
   故意改坏实现，测试是否变红。不会变红的测试是负资产
   （占时间、给假安全感），应删除或重写。
4. **测试与实现耦合**：断言私有实现细节、
   快照过大（整页快照，任何改动都要更新，无人真正审查）、
   大量 mock 导致测的是 mock 而不是代码。
5. **文本扫描式测试**：读源文件断言包含某字符串/CSS 类名/
   某行代码存在——这不是行为测试，重构必误报。
   除了确实需要守护的约定（可保留为显式的「约定检查」并注明理由），
   其余应迁移为行为测试或删除。
6. **错误路径断言**：是否断言了错误类型/错误码/用户可见信息，
   而不是只断言「抛了点什么」。
7. **时间与浮点断言**：硬编码时间戳、依赖当前时间、
   浮点精确相等（应用近似比较，与 C8-4 联动）。
8. **测试命名**：描述是否说明「在什么条件下期望什么」，
   还是 `it('works')`；失败时能否不看代码就知道坏了什么。

## I3 隔离、夹具与确定性

1. **测试间污染**：共享可变状态、全局单例、模块级缓存、
   数据库数据未清理、环境变量残留、
   `beforeAll` 中的状态被某个测试改坏。
   验证方法：单独跑 / 乱序跑 / 重复跑是否仍通过。
2. **执行顺序依赖**：是否存在必须按顺序跑的测试（应消除）。
3. **并行安全**：并行执行时的端口/临时目录/数据库/文件冲突；
   是否因并行问题而被迫串行（拖慢套件）。
4. **mock 策略**：mock 边界是否在外部依赖处（而非内部实现）；
   mock 未在测试后恢复；
   全局 fetch/时钟/随机数替换是否泄漏到其他测试；
   mock 的响应结构是否与真实接口一致（漂移的 mock 让测试说谎，与 E4-1 联动）。
5. **夹具健康**：夹具是否与当前 schema 一致、
   是否有重复的近似夹具、
   是否有共享工厂函数（而非每个测试手搓对象）、
   夹具中是否含真实用户数据（与 B7 联动）。
6. **外部依赖**：测试是否访问真实网络/第三方 API/生产数据库
   （不稳定且危险）；
   是否有录制回放或本地替身（容器化依赖优于全 mock）。
7. **不确定性来源**：时间、时区、随机、并发调度、
   map/set 迭代顺序、浮点、locale、机器性能（固定 sleep 等待）。
8. **flaky 清单**：是否有已知偶发失败被忽略/重试掩盖；
   建立 flaky 台账并定级（flaky 测试会训练团队忽略红灯，按 High 处理）。

## I4 套件结构与成本

1. **耗时**：总耗时与最慢的若干测试；
   本地反馈循环是否已难以承受（影响所有人每天，与 K3 联动）。
2. **分层可选执行**：能否只跑受影响范围（watch/变更检测/分片）；
   快慢测试是否分离（快门禁 + 慢夜间）。
3. **重复与冗余**：相同行为被多处重复测试、
   相同 describe/it 描述、
   跨包复制粘贴的测试、
   同一逻辑在单测与 e2e 各测一遍（保留更有价值的一层）。
4. **测试文件组织**：位置约定是否统一（同目录 vs 独立 tests 树）、
   命名是否统一、
   过大的测试文件（难定位）与过碎的测试文件。
5. **测试工具链**：配置是否集中、
   公共 setup 是否复用、
   覆盖率/报告/CI 集成是否可用。
6. **过期测试**：引用已删除 API、
   硬编码的计数/清单（文件数、skill 数、迁移数——
   每次新增都要改测试，属于脆弱守卫，需改为结构性断言）、
   长期 `skip`/`todo` 的测试（要么修要么删，带记录）。

## I5 缺失测试类型盘点

按「是否值得」逐项判断并给出建议（不是一律都要加）：

| 类型 | 何时值得 | 缺失影响 |
|------|---------|---------|
| 集成测试（真实 DB/队列） | 有持久层 | 事务/约束/迁移类缺陷无法被发现 |
| 契约测试 | 对外 API/库/事件 | 破坏性变更静默发布 |
| e2e 关键旅程 | 有 UI、旅程跨多模块 | 组合失效无人发现 |
| 授权矩阵测试 | 多角色/多租户 | 越权长期存在（最高性价比的缺失项） |
| 属性测试 / 模糊测试 | 解析器、序列化、算法、输入校验 | 边界输入崩溃 |
| 并发测试 | 有竞态风险的写路径 | 线上偶发数据错乱 |
| 迁移测试 | 有迁移 | 升级时数据损坏 |
| 性能基准 | 有性能要求的热路径 | 回归无感知 |
| 负载/容量测试 | 面向规模的服务 | 过载行为未知 |
| a11y 自动检查 | 有 UI | 可访问性回归 |
| 视觉回归 | UI 稳定且重要 | 样式破损 |
| 快照/审批测试 | 复杂输出（报告、生成文件） | 输出漂移 |
| 变异测试 | 核心算法且已有较好覆盖 | 测试有效性未知 |
| 安全回归测试 | 已修复过的安全问题 | 同一漏洞复发 |

对每个「应该有但没有」的类型，给出最小起步方案（先覆盖哪 1-2 个场景），
不要提「建议引入 X 测试」而无落地路径。

## I6 测试债清理

1. 删除无效测试（I2-3 验证不会变红的）、
   合并重复测试（I4-3）、
   强化弱断言（I2-1）、
   迁移文本扫描测试（I2-5）。
2. 清理 `skip`/`only`（`only` 泄漏进主干会让其余测试全不跑——**按 High 处理**）。
3. 补齐缺失的清理逻辑（临时文件、测试数据库、全局替换）。
4. 统一测试风格与公共工具（断言辅助、工厂、fixture loader）。
5. **清理必须可验证**：每次删/改测试后，确认套件仍能捕获原本要守护的行为；
   删除测试的理由写进台账（删测试是减少保护，必须留痕）。
