# 严重度评级与报告格式

## 严重度标准

按**后果**分级，不按修复难度、不按代码丑陋程度。

| 级别 | 判据 | 处理时机 |
|------|------|---------|
| **Critical** | 已经或极易造成：数据泄露 / 未授权访问 / 数据丢失或损坏 / 服务不可用 / 资金损失 / 合规违规。无需特殊条件即可触发，或已在生产发生。 | 立即修（或立即上报，若属禁止自动修类别） |
| **High** | 在常见条件下导致功能错误、数据不一致、安全防护缺失但有缓解、关键路径无测试保护、会让团队忽略告警（flaky、`only` 泄漏）。 | 本轮必修 |
| **Medium** | 特定条件下出错、影响可维护性且有明确代价、体验缺陷、局部性能问题、文档错误会误导开发。 | 本轮批量修或记 deferred |
| **Low** | 一致性、可读性、轻微体验、优化机会。 | 能顺手修则修，否则记账 |
| **Info** | 结论性观察、不是缺陷（例如「此处设计合理，原因是…」）。 | 只入报告正文，不入台账 |

### 提级与降级规则

- 在**信任边界**上 → 提一级。
- 可被**外部未认证用户**触发 → 提一级。
- 影响**全部用户/全部租户** → 提一级。
- 漏洞代码**不可达**或需要管理员权限 → 降一级，并写明可达性判断依据。
- 有**有效缓解**（限流、WAF、前置校验）→ 降一级，写明缓解在哪。
- **重复出现同一根因 ≥3 处** → 作为一条模式型发现，按最高实例定级，不拆成 N 条。

### 禁止的定级理由

「看起来不规范」「我更喜欢另一种写法」「可能将来会有问题」
——没有具体后果就不是发现。

## 单条发现格式

```markdown
### [F-B2-003] [High] 批量归档接口缺少租户归属校验

- **维度**：B2 授权与多租户隔离
- **位置**：`src/api/archive.ts:64-78`（同类：`src/api/restore.ts:41`）
- **现象**：按 `ids` 批量归档时只校验了单条路径的权限，批量路径直接按 ID 更新，
  未附带 `tenant_id` 条件。
- **后果**：任意已登录用户可归档其他租户的记录（跨租户数据破坏）。
- **触发条件**：认证用户构造任意 ID 数组调用该接口，无需特殊权限。
- **证据**：`archive.ts:71` 的 update 语句 where 子句只有 `id IN (...)`。
- **建议**：在仓储层为所有写操作强制注入租户条件；
  该接口改为调用 `archiveForTenant(tenantId, ids)`。
- **回归保护**：新增测试「用户 A 调用归档传入 B 租户 ID → 期望 403 且数据未变」。
- **固化**：架构 lint 禁止在 api 层直接调用 db update（交 L4）。
```

字段要求：

- **位置必须是 `file:line`**；没有行号的发现不收。
- **后果必须具体**（谁受影响、怎么受影响），不写「可能有安全风险」。
- **触发条件**决定严重度，必须写。
- **建议**要可执行，指出改哪里、改成什么；大改动给出分步方案。
- **回归保护**：Critical/High 必填（与 I1-2 联动）。
- 同类位置列在同一条里，不要刷条数。

## 发现台账 `audit/findings.md`

所有 agent 的发现最终汇总到一张表，ID 全局唯一且稳定：

```markdown
| ID | 级别 | 维度 | 标题 | 位置 | 状态 | 处理 |
|----|------|------|------|------|------|------|
| F-A1-001 | Critical | A1 | 生产 DB 连接串提交在历史中 | `.env.bak:3` | reported | 需人工轮换 |
| F-B2-003 | High | B2 | 批量归档缺租户校验 | `src/api/archive.ts:71` | verified | 已修 + 测试 |
| F-J3-014 | Medium | J3 | 订单服务 900 行混合四种职责 | `src/order.ts` | deferred | 需设计评审 |
```

状态流转：`open → fixing → fixed → verified`，或
`deferred`（带原因与 owner）/ `wontfix`（带理由）/ `reported`（禁止自动修类）。

ID 规则：`F-<维度ID>-<三位序号>`。**ID 一旦分配不得复用或重编号**
（报告、提交信息、测试名都会引用它）。

## 波次报告 `audit/<wave>/<agent-id>-<slug>.md`

每个审查 agent 输出一份，结构：

```markdown
# W2-3 B3 注入与输入校验（scope: src/api, src/workers）

## 审查范围与方法
- 读取的文件清单 / 枚举的入口清单 / 使用的搜索模式
- 未能覆盖的部分与原因（时间、权限、需运行环境）

## 发现
（按严重度降序，使用上面的单条格式）

## 模式型发现（交 W12 横向展开）
| 模式 | 典型实例 | 搜索特征 | 预估规模 | 可否 lint |

## 已确认无问题的项（Info）
简述检查过什么、为什么判定没问题——这是覆盖率可复核的依据

## 未决问题
需要人工判断或需要领域知识才能定性的项
```

「已确认无问题的项」不是形式主义：没有它，无法区分
「查过了没问题」与「根本没查」。

## 报告纪律

1. **不夸大**：不写「修复了 200 个问题」而实际多数是格式统一。
   按严重度分别计数。
2. **不隐藏失败**：门禁没过、某维度没查完、某修复没验证，必须写进报告。
3. **凭据与敏感数据不进报告**：用 `path:line` + 前缀指纹代替实际值。
4. **可复核**：每条结论都能顺着 `file:line` 与命令被独立验证。
5. **给决策者用**：执行摘要要能被不读细节的人用来做「能不能发布」的判断。
